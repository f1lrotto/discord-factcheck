Two news channels.
One Jolanda.

Implementation plan and task contracts · Agent execution runbook

Keep the repository and Discord identity. Add news as an independent module alongside AI conversations and media reposting, with durable collection and delivery state.

Start in the existing process for this small workload. The same design can move into a separate news worker if independent uptime or heavier retrieval becomes necessary.

Channel A · Denník N

Important stories through the day

Collect the editorial importance selection every 20 minutes. Post individual embeds for new, eligible stories, with pacing and duplicate control. Collection frequency does not dictate message frequency.

Channel B · Aktuality

One daily edition

Collect Aktuality’s own roundup at 20:00 in Europe/Bratislava, with a 21:00 fallback only when no fresh edition was collected. Send one compact message. Use several short embeds or one structured embed, with a single notification opportunity.

02 / Current codebase

A small application with two feature paths

This is one Node.js / TypeScript package, built with pnpm and deployed as a long-running worker. src/index.ts constructs dependencies explicitly. The checked-in Dockerfile starts dist/index.js; the deployment documentation specifies one Railway replica. Live deployment settings were not inspected.

Both feature paths share the process and database infrastructure. Media already has its own work limits, persistence interface, and Discord transport.

AI conversations

Reactive, paid work

jolanda.ts coordinates authorization, conversation ownership, model calls, budgets, streamed responses, and shutdown. Public web tools belong to model turns.

Media reposting

A useful precedent

discord-reels.ts handles Instagram / TikTok independently of AI. ReelStore and ReelDiscordTransport separate persistence and delivery concerns.

Shared foundation

Already available

Zod configuration, MongoDB, Pino logging, time-zone helpers, admin commands, bounded work, and graceful shutdown. Budget recovery has a timer; news scheduling and an outbox do not exist.

Reuse the foundation and design patterns. News should not call jolanda.handleTurn(), use AI spending reservations, or pretend to be a user message. Publisher-selected news can run without any model calls.

03 / Deployment options

Repository, process, and identity are separate choices

A separate Discord bot gives a different account and permission scope. A separate process provides runtime isolation. A separate repository provides independent ownership and releases. None of these requires the other two.

Four ways to place the same collection and delivery logic
Option Placement Tradeoff When to choose it
RECOMMENDED START
A. News module in Jolanda 		One repo, one process, same bot. News owns collection, scheduling, and delivery. Smallest operational cost. Process failure, deployment, and resource pressure affect all features. Two sources, ordinary HTTP, low daily volume. Separate deadlines and bounded tasks keep expected failures local.
B. Separate news worker One repo, two processes. News collects and sends through REST using the same bot token, or channel webhooks. Independent restarts and resource limits. Another deployment; shared-token rate limits still apply. News must survive chat/media outages, or collection needs heavier browser work. No second Gateway login or command registration.
C. Collector worker + bot publisher A worker writes normalized items into MongoDB. The existing bot plans and sends messages. Scraping is isolated; news delivery still depends on bot uptime. Adds a producer/consumer contract. Several consumers need the same collected content, or centralized Discord delivery matters.
D. Independent news application Separate deployment, optionally separate repo and Discord account. Webhooks can avoid a bot account entirely. Independent permissions and releases, but duplicated configuration, persistence, monitoring, and maintenance. News becomes a separately owned product. Two channels alone do not justify it.
Bot REST versus channel webhooks

Same bot REST: preserves Jolanda’s identity and command integration, and supports deterministic message nonces. In option A, inject the existing client’s REST capability into a dedicated news publisher so it can share request coordination. In option B, a REST-only worker can use the same token without opening a Gateway session; coordinate rate-limit failures across workers.

Channel webhooks: useful for a standalone worker with a news-specific name and channel-scoped credentials. They add webhook lifecycle/secret management and have different retry/idempotency behavior. Both approaches support embeds. A webhook is a delivery adapter, not a scraping solution.

Existing transport: the media transport deliberately disables automatic retries and rejects rate-limit waits. Its interface requires an incoming Discord message to reply to. Reuse its finite-request approach; do not make scheduled news fabricate a source message.

What extracting a worker would actually change

Add a news-main.ts entry point and news-specific environment validation. The current loadConfig() requires an OpenRouter key and validates AI budgets; a standalone news process should not need them. Reuse Mongo connection helpers without starting AI accounting recovery. Use separate collection permissions where appropriate.

The current image includes Python, yt-dlp, and FFmpeg. A news-only image can omit them. Keep one owner for global command registration: discord-bot.ts replaces the application command list at readiness, so running a second copy is not a clean worker split.

04 / Proposed modules

Collection produces content. Policy decides delivery.

The source adapters understand publisher formats. The news module understands freshness, selection, scheduling, and receipts. The Discord adapter understands channels, embeds, permissions, and notification settings.

Source adapter / Denník N

Collect editorial importance

Retrieve the important listing’s initial structured data. Normalize stable IDs, source links, publication dates, excerpts, tags, and image metadata. Preserve first-seen and revision information; a post can become important after publication.

Check recent IDs again instead of advancing solely by publication timestamp. Do not interpret all RSS items, or the RSS category “Hlavná”, as important news.

Inspected important listing · page data is undocumented and needs parser-change detection.

Source adapter / Aktuality

Collect a complete edition

Discover a fresh roundup on its category listing; fetch that edition once. Return the edition ID/date and its selected story sections, with links where present. Do not split the roundup into unrelated feed entries before policy runs.

The tested roundups had seven stories. No dedicated, correct roundup RSS was verified. This is HTML retrieval, with a separate parser from Denník N.

Inspected roundup listing · weekday editions and occasional weekend weekly selections.

Keep normalization, eligibility, and digest formatting as pure functions. The source result should distinguish short stories from an editorial edition. An unchanged response, a valid empty feed, an access denial, and a broken parser must be different outcomes.

A practical first layout is src/news/ with index.ts, sources/dennikn.ts, sources/aktuality.ts, policy.ts, store.ts, discord.ts, and shared news types. This contains the new feature without relocating the existing flat source tree.

Two audiences, two independent schedules. The daily channel should remain a useful complete roundup even if a story also appeared in the continuous channel. Deduplicate within each channel; do not automatically remove daily stories merely because they appeared in Channel A.

05 / Reliable delivery

The database remembers what the timer cannot

A timer wakes the module. MongoDB decides which work is due and which instance owns it. That distinction protects against restarts, overlapping deployments, delayed editions, and ambiguous network responses.

news_sources

Collection state

ETag / Last-Modified, next poll time, backoff, last successful parse, freshness, and an expiring owner lease. Fetch once per source for all configured destinations.

news_items

Normalized content

Source + item ID, source publication time, first seen, last changed, content hash, optional metadata, and edition membership. Keep a bounded recent history for promotion and duplicate checks.

news_deliveries

Outbox and receipts

A durable record of the intended destination and frozen payload, due time, owner/lease, attempts, outcome, and usable message reference where edits are supported.

  1. Collect independently. Begin with bounded HTTP, source-specific polling intervals, conditional requests, and backoff. A source failure must not stop the other source or the AI/media paths. Never make Discord retry by scraping the source again.
  2. Plan by publication mode. Live mode selects new important stories, groups near-duplicates, applies pacing and a soft daily budget. Daily mode selects one fresh edition for a date in Europe/Bratislava. The confirmed collection times are 20:00 and a conditional 21:00 fallback; skip the day if neither finds a fresh edition.
  3. Reserve atomically. Unique live key: destination + source + item ID. Unique daily slot: destination + local calendar date, with the chosen edition ID attached. Read-then-send checks alone are insufficient. Reservations and the state they consume must be committed atomically, or recoverably through unique upserts.
  4. Publish once, record the result. Claim a due outbox entry, check owner/lease before sending, then record the receipt. Reclaim safe pre-send work after expiry. Ownership tokens prevent a stale worker from committing transitions; they do not make Discord part of the Mongo transaction.
  5. Treat uncertain sends separately. Discord may accept a message just before the process dies. Use a stable nonce for short-window retries, then reconcile with a bounded channel-history check or hold as uncertain. Never blindly replay a whole digest after an ambiguous send. Prefer a missed alert over a duplicate alert if reconciliation cannot establish the result.
  6. Recover without a flood. First installation establishes a baseline. Restart recovery handles only a bounded fresh backlog. Expired delivery receipts must not make old content eligible again. Keep tombstones longer than the allowed replay window.
Continuous channel

One story, one useful update

Use source IDs for exact duplicates and title/content fingerprints for obvious story duplicates. Those fingerprints will not perfectly group every event. Automatic editing of delivered messages is deferred in the implementation plan. Do not turn minor revisions into new alerts.

Silence pushes by default if desired; cadence, quiet hours, sports filtering, and the approximate 15-story budget remain channel policy.

Daily channel

One message, at most one ping

One message can hold up to ten embeds, with 6,000 aggregate embed-text characters. Fit the entire edition within that budget; reduce individual summaries or use one list embed rather than emitting a second message.

All section embeds must not share the same embed URL: Discord deduplicates them. Use actual story links when available, or one roundup embed with sections. Missing article images should not trigger seven extra fetches by default.

Confirmed daily publication policy: use Aktuality’s own fresh roundup and skip days without an edition. Wait only within a bounded evening window when it is late; do not substitute an automatically generated digest or replay yesterday’s edition. This means at most one daily message, rather than a guaranteed message every day.

Destination IDs and message edits need an explicit storage decision

The existing Mongo store persists Discord identifiers as HMACs. That works for reactive lookups because an incoming event supplies the real IDs. A hash cannot recover a channel to post to later, nor recover a message ID for an edit.

Confirmed initial setup: configure destinations through bot commands. Persist encrypted, retrievable guild/channel references with HMAC lookup keys. Automatic message edits are deferred; ambiguous sends remain uncertain unless their outcome can be established.

Command-configured subscriptions: an enumerable subscription store needs authenticated encryption, context binding, and a documented key lifecycle. Do not copy ReelStore.setEnabled() and expect its hashed key to be an enumerable address book. Configuration changes must cancel/replan pending deliveries so old work does not leak into a newly selected channel.

Safety and shutdown belong inside the news module

Allow only the two publishers and their expected image hosts, validate redirects, cap response bytes, and parse structured JSON without evaluating page scripts. Reuse low-level address-validation ideas where appropriate; the current media HTTP module is specialized for Instagram/TikTok.

Start collection after configuration/database initialization. Gate sends on destination validation and Discord readiness. Stop timer admission on shutdown, abort pending fetches, settle or mark sends uncertain, drain owned work, and only then close Discord and MongoDB. Do not detach promises that survive shutdown.

Log source health, freshness, item counts, delivery outcomes, retries, and time since the last successful edition. Never log webhook tokens or raw Discord identifiers. A publisher outage should surface in admin diagnostics, not generate repeated public-channel failure messages.

Discord’s nonce deduplication covers only the past few minutes; it is not a permanent exactly-once guarantee. Notification delivery also depends on member settings. Discord message, embed, nonce, and notification contracts.

06 / Change & validation

Contained work, with a few deliberate integration points

src/index.ts
Construct the news module and its adapters. Add its start/stop/drain work to the existing lifecycle.
src/config.ts
Validate the deployment kill switch and dry-run mode. Destinations are configured through commands and stored as encrypted routing references. Secrets remain deployment configuration.
src/mongo-store.ts + schema
Add a separate store.news interface and news indexes. Share the Mongo client; keep news receipts out of AI request/accounting collections.
src/discord-bot.ts
Expose/inject a narrow sending capability and readiness signal as needed. The current returned interface exposes lifecycle methods only.
src/discord-commands.ts
Required admin commands select a channel for each feed: /jolanda continuous feed and /jolanda daily feed. Add disable operations and feed status.
src/news/ — proposed
Own collection, normalized content, scheduling, outbox behavior, rendering, and diagnostics. Most feature changes stay here.
src/discord-response.ts
Keep the AI renderer’s embed suppression. News uses its own renderer with validated source URLs; do not weaken AI output rules.
README.md + SECURITY.md
Document scheduled posting, destination retention, source attribution, new permissions, receipts, and the chosen notification behavior.
How people replying to news interact with the existing AI

Incoming bot/webhook messages are ignored, so publishing news does not start an AI loop. Ordinary replies continue AI conversations only when the referenced message belongs to the conversation-link store. News receipts must stay separate.

An explicit mention while replying can start a new AI request, but current reference extraction reads message.content, not embed text. If “ask Jolanda about this news embed” becomes a feature, add a deliberate lookup of the normalized news record. It is not automatically provided by sharing the bot identity.

Implementation order and meaningful tests
  1. Collector preview: fixtures from both publisher formats, bounded anonymous fetching, field normalization, fresh-edition detection, and no Discord writes. Detect malformed pages separately from valid empty results.
  2. Durable policies: Mongo uniqueness/lease tests, first-run baseline, restart recovery, late importance promotion, duplicate events, and retention longer than replay eligibility.
  3. Delivery preview: render the exact live/daily payloads; verify aggregate embed limits, valid source links, optional images, and explicit allowed mentions.
  4. Failure paths: 304/403/429, parser changes, missing/late editions, DST and local midnight, permission loss, two overlapping workers, lease loss during send, timeout after acceptance, and shutdown during fetch/send.
  5. Controlled rollout: preview the proposed output over several days, then enable the two chosen channels. Keep collection health and message volume visible through admin status.

pnpm format and pnpm check are the repository gates. Production source availability and Discord delivery require a later explicit operational test; passing unit tests does not verify publisher access from Railway.

Recommended first implementation: option A, direct HTTP for both sources, a separate news module, Mongo-backed collection/delivery state, and the existing bot identity. Move that module to option B when independent uptime becomes worth another deployment. A second Discord account is a product/permissions choice, not a prerequisite for reliable news.
